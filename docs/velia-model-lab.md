# Исследования VELIA в Velyon Core

Панель `/admin/research` использует существующий вход владельца через Telegram,
проверку `ADMIN_ID`, сессионные cookies и CSRF. Действия и выгрузки отражаются
в журнале аудита. Доступ к результатам и данным обучения есть только у владельца.

## Что доступно

- Исследование методов улучшения Flash: цель, до двух поисковых запросов,
  один логический запрос настроенной исследовательской модели, гипотезы,
  риски и план проверки. Возможны внутренние повторы провайдера.
- Отчёт сохраняет ссылки и поисковые выдержки. Допускаются HTTPS-ссылки с
  доменов PrismML, arXiv, Hugging Face, GitHub, OpenReview и Microsoft.
  Это фильтр источников, а не подтверждение научной достоверности. Полные
  материалы здесь не загружаются. Несуществующие идентификаторы ссылок
  в ответе модели отклоняются. Внешний текст передаётся как недоверенные данные.
- Диагностический набор `flash-quality-v1`: восемь задач с точными критериями
  и две с ручной оценкой. Ещё до четырёх подтверждённых пользовательских
  контрольных задач включаются в следующий запуск. Ответы, ошибки,
  параметры генерации и время каждого запроса сохраняются.
- Сравнение двух завершённых прогонов допускается при одинаковых задачах,
  критериях, коде клиента и параметрах генерации. Автоматическая оценка
  относится только к закрытым задачам; ошибка или обрезанный ответ на них
  считается неуспехом. Открытые ответы оценивает владелец отдельно.
- Примеры с эталонами имеют неизменное назначение `train` или `holdout` и
  отметку ручной проверки. JSONL экспортирует только проверенные `train`.
  Встроенные экзаменационные вопросы нельзя напрямую добавить в обучение.
  Переформулировки и другие семантические утечки исключает владелец.

Название запуска — заметка владельца. `VELIA_FLASH_MODEL_REVISION` — метка
ревизии из конфигурации, не аттестация весов worker API. Результат малого,
стохастического набора нельзя выдавать за доказательство общего роста
интеллекта. Для решения о выпуске нужны повторные прогоны, более широкий
независимый набор и разбор регрессий.

## Выполнение

Задания, снимки задач, ответы и примеры хранятся в PostgreSQL, не в памяти
веб-процесса. При регистрации админки Core запускает один фоновый daemon
thread через `cleanup_ctx`; сеть и БД не блокируют цикл aiohttp. Поток работает
только с заданиями, которые владелец запустил вручную. В режиме ожидания
он проверяет очередь раз в три секунды и пишет heartbeat раз в двадцать секунд.

Один шаг проверки качества — один запрос к текущему Flash с его штатным
промптом и параметрами. Общая advisory-блокировка `velia:flash:worker`
предотвращает одновременную генерацию с пользовательским Flash. При занятости
задание возвращается в очередь на 15 секунд; между задачами есть пауза.
Текущий лабораторный запрос не прерывается при появлении пользовательского.
Поэтому продолжительные диагностические прогоны лучше запускать вне пика.

Очередь ограничена четырьмя незавершёнными заданиями, данные — тысячей
примеров на владельца. Claim сериализуется advisory-блокировкой и использует
`FOR UPDATE SKIP LOCKED`. Lease — десять минут, допускается два восстановления
после истечения lease. Каждый claim получает новый fencing token.
Старый worker и отменённое задание не могут записать ответ или финальный статус.
Завершённые шаги повторно не исполняются. Потерянный до записи запрос при
восстановлении может выполниться ещё раз, включая повторную оплату провайдера.

Встроенный процесс останавливается при завершении Core. Он daemon и не
удерживает остановку дольше пяти секунд; прерванное задание восстанавливается
после истечения lease. Отмена сохраняется сразу, хотя текущий сетевой запрос
может завершиться позже. Его результат отклоняется.

Отдельный `run_velia_research_worker.py` также поддерживает эту очередь.
Он берёт только задания своего `ADMIN_ID` и типов, для которых у него
настроены ключи и endpoints. Копировать ключи в этот сервис для обычного
использования админки не требуется: встроенный worker Core использует
конфигурацию Core. Несколько реплик координируются через PostgreSQL.

## Конфигурация

| Переменная | Назначение |
| --- | --- |
| `VELIA_MODEL_LAB_ENABLED` | Включение лаборатории; по умолчанию `true`. |
| `VELIA_MODEL_LAB_EMBEDDED_WORKER_ENABLED` | Встроенный worker Core; по умолчанию `true`. |
| `ADMIN_ID` | Единственный владелец панели и заданий. |
| `VELIA_FLASH_*` | Существующая конфигурация Flash, без её изменения. |
| `VELIA_FLASH_MODEL_REVISION` | Необязательная метка версии весов. |
| `WEB_SEARCH_PROVIDER`, `WEB_SEARCH_API_KEY` | Существующий Tavily, Serper или Bing. |
| `LLM_PROVIDER_RESEARCH` | Gemini или Kimi; иначе `LLM_TEXT_PROVIDER`, затем `LLM_PRIMARY_PROVIDER`, затем Gemini. |
| `GEMINI_API_KEY` / `KIMI_API_KEY` | Ключ выбранного исследовательского провайдера. |

Исследование вызывает существующий шлюз модели с учётом его разрешений,
повторов и учёта использования. Генерация ограничена запросом на 1800 токенов.
Кнопка сообщает владельцу о возможной оплате поиска и модели. Вызовы
по расписанию, автоматическое обучение и переключение боевой модели отсутствуют.

## Следующий этап: изменение весов

Сначала нужен подтверждённый путь обучения для конкретного checkpoint Bonsai
и сборки runtime. Исследовательский отчёт должен различать LoRA, дистилляцию,
повторную квантизацию и изменение промпта. LoRA добавляет файл адаптера;
поддержку тренировки непосредственно в формате Bonsai PQ2 нельзя предполагать.
Совместимость нужно подтвердить до выделения compute и запуска обучения.

Будущий обучающий pipeline должен сохранять исходный checkpoint, checksum,
версию данных, параметры обучения и итоговые артефакты. Отдельный кандидат
проверяется на неизменном holdout, регрессиях, размере файлов и пиковом RAM.
Только после этих измерений можно обсуждать улучшение весов при сохранении
компактности Bonsai. Этот PR не изменяет веса и не заявляет такого улучшения.

## Проверка

```bash
python3 -m pytest -q tests/test_velia_model_lab.py tests/test_velia_flash.py tests/test_velia_admin_mobile_ui.py
```

Для тестов транзакций, восстановления, отмены и выгрузки укажите отдельную
тестовую PostgreSQL-базу в `VELIA_MODEL_LAB_TEST_DATABASE_URL`. Для каждого
теста создаётся и удаляется изолированная схема. Обычный `DATABASE_URL`
никогда не используется этими интеграционными тестами. Вызовы моделей и поиска
заменяются тестовыми ответами, платные запросы не выполняются.

Проверку конкурентных advisory-блокировок и нескольких реплик проводите
на обычном PostgreSQL: эмуляторы с одним backend не подтверждают эти свойства.
Workflow `VELIA Model Lab` использует PostgreSQL 16 и включает такие тесты
через `VELIA_MODEL_LAB_NATIVE_POSTGRES_TESTS=1`.
